Integration contract for lead-owned backend and frontend:
GET /api/ai/status -> {enabled:boolean}; no provider identity/secrets needed.
POST /api/ai/chat JSON {session_id:string, request_id:string, revision:number, messages:[{role:'user'|'assistant',content:string}], draft:{kind:'brew'|'bean'|'grinder'|'brewer',fields:Record<string,unknown>}}. Flat leaf keys exactly as DraftEngine; pours atomic. Initial kind brew with empty fields is provisional; model may return another kind ONLY while no meaningful draft fields exist. Otherwise return reply asking explicit new session (no silent kind swap).
Response {reply:string,kind:DraftKind,patch:Record<string,unknown>,choices:[{label:string,patch:Record<string,unknown>,brewer_type?:string}],brewer_type?:string}. IDs token stay client-side; no need echo. Patch values null clear; absent unchanged. Server validates all fields/references, derives brewer_type from real selected own brewer. Library lookup bounded own-store data; raw model choices never trusted. Client creates Choice with request token before applyChoice. No tool execute requirement: initial app service can ask for constrained JSON content (no strict response_format requirement); transport already supports tools for future. Error uses existing APIError envelope.
Save through existing createBrew/createBean/createGrinder/createBrewer only. No writes during chat or choice selection. Homepage bar only when authenticated AND status enabled. /chat direct-load route supported even disabled (clear unavailable state). Session local scoped by DID, no session picker initially.
