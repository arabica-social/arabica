## Agreed product behavior

- Creation of brews, beans, grinders and brewers. Existing PDS schemas, units,
  create validation, mutation APIs, and legacy-record compatibility stay intact.
- Authenticated homepage: one textarea, placeholder "Describe a brew or bean",
  send button inset at right, aligned with the feed. No headings, surrounding
  panel, example pills, slogans or extra explanatory copy. Grows while typing.
  This applies to the AI entry block, NOT the existing Community masthead: keep
  Community H1, manual Log Brew/Finish setup and signed-in feed filters intact.
- Sending opens a dedicated maximized /chat SPA route. Preserve the ordinary
  homepage/manual logging paths. Hide AI entry when unconfigured.
- Conversation can ask for missing information or offer actual own-library
  matches as clickable choices. Do not auto-select ambiguous matches. Clicking
  a choice updates the real reference locally; no model round trip required.
- Show editable form inputs when the draft has enough meaningful information,
  not a blank form at the first turn and not only after every optional field is
  collected. Reveal bean at name+origin; equipment at name; brew at bean+brewer
  references or one reference plus two substantive preparation/result fields.
  Once revealed, keep the editor visible through edits; offer explicit Open form
  for manual completion. These display rules do not tighten save validation.
- No decorative Brew/from-your-journal header or selected-record pills. Real
  values and useful controls own the hierarchy. Do not invent omitted values.
- Save button is the only write authority. All writes use existing authenticated
  mutation APIs. Add a targeted TODO for future confirmed conversational saving;
  do not implement a model write tool or save on "save it" in this iteration.
- One active record draft per chat session. Switching record kind is explicit
  and cannot discard a draft. Multiple-session storage is designed now; a session
  picker and cross-device history can be deferred.
- Preserve conversation and draft across reloads, scoped to account DID. Explicit
  discard; no silent eviction of unsaved work. Saved cards link to records.

## Draft ownership and concurrency contract

- A single canonical draft feeds chat context and form controls.
- Each request is bound to session ID, request ID and a snapshot revision.
- Track per-field revisions. A response cannot overwrite fields changed after
  its request started; apply proposals as one batch and report skipped changes.
- A later explicit chat instruction sees current fields and may revise them.
- Direct clicks on stale library choices must not silently replace newer picks.
- Reuse dependent-field safety: grinder changes may clear grind setting; brewer
  category changes may invalidate method fields. Ask before destructive changes.
- One-level Undo last AI change restores only still-unmodified affected fields,
  never erases subsequent direct edits. Undo must pass dependent-field safety.
- Save disabled while a response is pending, with Stop available. Stop invalidates
  request before aborting fetch. Saved/discarded drafts reject late responses.
- Switching sessions does not retarget responses or destroy pending state.

## Ownership and implementation seams

- `internal/ai`: app-agnostic provider configuration and bounded OpenAI-compatible
  HTTP transport. Standard library; no provider SDK needed initially.
- `internal/arabica/ai`: coffee schemas, grounding, allowlisted operations and
  prompt policy. No shared package imports this package.
- Arabica handlers/routes: authenticated chat API and explicit /chat route.
  Compose service through app-owned routing/bootstrap seams, not coffee imports
  into shared server code. Load configuration once, not per request/render.
- `web/src/lib/ai`: typed state, draft reconciliation and persistence; components
  and routes own rendering. New/refactored composable editors are welcome. Do not
  destabilize existing full-page forms merely to maximize reuse.
- Existing mutation endpoints remain the only PDS write path. No new lexicons,
  feed, Explore or visibility policy changes.

## Provider and trust boundary

- `ARABICA_AI_CONFIG` overrides the default `./ai.json` (process working
  directory). A missing default disables the feature; invalid/unreadable config
  or a missing explicit override fails clearly. Supply `ai.example.json` with replaceable endpoint/model
  and `api_key: "${ARABICA_AI_API_KEY}"` interpolation, never real credentials.
  The server also accepts a literal `api_key`; keep credential-bearing files private.
- Configured server endpoint only; browser/model cannot select arbitrary URLs.
  Local HTTP providers allowed intentionally. Do not forward credentials across
  redirects. Redact upstream errors; no credentials/prompt bodies in logs.
- Tools mean only application-defined read/draft operations, never arbitrary
  execution, browsing, filesystem access or writes. Structured JSON and tools
  are transport encodings, not authorization. Keep operation validation separate.
- Transport choice needs a provider smoke test; do not silently require strict
  JSON-schema support from every OpenAI-compatible provider or build automatic
  fallback/retry that multiplies costs. Start non-streaming.
- Public record details may go to provider. Send relevant compact data only;
  omit handles/DIDs and unnecessary history. Server resolves opaque own-library
  choices back to real references. Untrusted record text cannot grant capabilities.
- Require auth + same-origin protection; rate/concurrency limits per account,
  body/turn/tool-round/output caps, timeout and cancellation. Bound limiter state
  and clean expired entries. Refuse unrelated tasks with a short coffee redirect.

## Initial browser/API contract (to finalize before HTTP/UI integration)

- GET /api/ai/status: availability only; never provider secrets.
- POST /api/ai/chat: bounded conversation, current typed draft and correlation IDs.
- Response: assistant text, validated partial draft proposal, validated library
  choices. Never model-authored HTML or arbitrary actions. No write endpoint.
- Draft kinds: brew | bean | grinder | brewer. Fields use existing API input keys
  and human/API units (not lexicon-scaled integers). Null clears explicitly;
  absent keys mean unchanged. Leaf paths support safe nested-field revisioning.
- Correlation IDs are client routing aids, not server ownership/authentication.
  Never trust client-supplied library records as authorization evidence.

## Growth and recovery

- Keep up to 20 locally persisted sessions per DID, with separate clickable
  history and an active-session pointer. Schema 2 reads the original single-chat
  schema without deleting it. Bound messages to 40 and user text to 4000
  characters each; bound storage to 256 KiB per chat and 2 MiB per account. Warn at limits; never silently delete
  an unsaved draft or truncate its meaning. Explicit New/discard resets safely.
- Never persist API keys or pending promises. Reload marks interrupted requests
  stopped; account changes abort requests and clear in-memory previous-account data.
- Storage failures leave live draft intact and tell user persistence is unavailable.
- Provider/auth/network errors retain draft, expose Retry/Stop as appropriate.
- Review exact backend caps and schema with implementation tests before integration.

## Implemented follow-up: roaster-aware beans and saved recipes

The names-only catalog was insufficient for requests such as “brew with bean
from Recluse, Orea 3 pour recipe.” The app-owned read-only projection now joins
own bean-to-roaster and recipe-to-brewer relationships from full AT-URIs, includes
open/closed status and full-library ambiguity counts, and supplies actual saved
recipe amounts, pours and instructions. Relevant/open records and selected refs
are prioritized within 100 items per existing type and 20 recipes. Underlying
PDS collection reads still materialize records; this is not a bounded database
query or an exhaustive provider search.

The service allows an own recipe reference, attaches validated stored defaults,
and couples ambiguous identity and all preparation values behind a choice.
Ordinary provider choices remain reference-only; recipe choices may carry
allowlisted preparation facts from saved instructions or explicit user text.
Own linked brewers are
authoritative relationships, not fuzzy name guesses. Existing recipe references
do not reset later manual values. Browser revision guards protect whole recipe
proposals and later manual recipe/brewer changes; only Save invokes the existing
brew mutation API, preserving the normal recipe reference. The native editor
exposes own recipe details but does not infer brewer ownership from the legacy
API's bare rkey. Recipe pour start times never become bloom durations. No schema,
unit migration, provider/model config, external search or write tool was added.
